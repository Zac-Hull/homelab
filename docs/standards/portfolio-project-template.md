## Overview

Briefly explain what this project is and why it exists.

This section should answer:

- What did I build, rebuild, or investigate?
- Why was it worth doing?
- Why does this project belong on the site?

Aim for one to three short paragraphs.

## Problem This Project Solves

Describe the problem, gap, pain point, or opportunity that created the project.

This could be:

- A technical limitation
- A reliability issue
- A cost concern
- A workflow inefficiency
- A security concern
- A desire to learn a system through practical use

Focus on the real reason the project became necessary or valuable.

## Goals

List the most important outcomes you want from the project.

- Goal 1
- Goal 2
- Goal 3
- Goal 4

Good goals are concrete enough to evaluate later.

## Environment or Constraints

Describe the context that shaped the project.

Possible details:

- Existing infrastructure
- Budget limitations
- Hardware constraints
- Network constraints
- Security requirements
- Skill level at the time
- Need to avoid downtime or preserve working systems

This section is especially useful when the project is about choosing a path, not just installing a tool.

## Planned or Final Architecture

Explain how the solution is structured.

Use bullets if helpful:

- Component 1 and its role
- Component 2 and its role
- Component 3 and its role
- How traffic, data, or control flows between them

If the project is still underway, use **Planned Architecture**.  
If it is complete, use **Final Architecture**.

## Design Decisions

Explain the major choices you made and why.

Examples:

- Why this platform instead of another?
- Why self-hosted instead of managed?
- Why split services apart?
- Why use a static architecture?
- Why automate later rather than immediately?
- Why rebuild instead of repair?

This is one of the most valuable sections on the page because it shows your reasoning, not just the end result.

## Implementation Path

Walk through the project in stages.

1. First major step
2. Second major step
3. Third major step
4. Validation or cutover step
5. Follow-up or cleanup step

This does not need to be a command-by-command runbook unless the project calls for it. The goal is to show sequencing and intent.

## What I’m Learning

Explain what this project is teaching you.

- Concept or technology 1
- Concept or technology 2
- Operational lesson 1
- Tradeoff or decision-making lesson
- Documentation or troubleshooting lesson

This is a great place to make the growth visible without sounding apologetic.

## Current Status

Describe exactly where the project stands today.

Examples:

- What is already working
- What has been validated
- What is still in progress
- What has not started yet
- What would need to happen before status changes

Keep this honest and specific.

## Planned Improvements

List meaningful next steps that improve the project rather than vague “maybe someday” ideas.

- Improvement 1
- Improvement 2
- Improvement 3
- Improvement 4

## Lessons Learned

Use this section once the project has produced clear takeaways.

Possible prompts:

- What surprised me?
- What would I do differently next time?
- What failure or friction changed my approach?
- Which design choice proved especially valuable?
- What became easier to understand only after doing it?

If the project is still early, you can omit this section until later.
